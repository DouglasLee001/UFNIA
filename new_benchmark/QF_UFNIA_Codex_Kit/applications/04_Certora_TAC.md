# Certora TAC：新合约验证条件的 QF_UFNIA 提取

## 交给 Codex 的目标

选择新的公开合约输入、代码版本或验证性质，经真实验证前端生成验证条件，提取符合 QF_UFNIA 的子集。每个实例必须能解释为某个合约操作及性质的反例检查。不要直接复制 SMT-LIB 旧 Certora 家族，也不要把任意合约 SMT 输出通过改头部变成 QF_UFNIA。

本任务书基于已核实的仓库文档，没有实际运行 Certora 或 ctac。上游 TAC 生成、可用许可证和该版本的输入格式都必须在实施时确认。开源 ctac 并不意味着它能独立完成从 Solidity 到 TAC 的编译。

## 已核实材料

- 新输入候选集：<https://github.com/fsainas/contracts-verification-benchmark>。README 描述 323 个验证任务，提供多种正确或含缺陷合约版本，涵盖 Constant-product AMM、Vault、Payment Splitter 等用途。论文为 *Towards Benchmarking of Solidity verification tools*，FMBC 2024。数量是调研时仓库描述，不是 323 个已确认的 QF_UFNIA 文件。
- 导出工具：<https://github.com/1arie1/ctac>。文档说明其读取 Certora 的 `.tac`、`.sbf.json` dump，可导出 SMT-LIB；默认 `sea_vc` 编码标为 QF_UFNIA，采用 DSA、控制流可达性、整数范围约束以及 bytemap 的 UF 表示。
- 既有来源核对：<https://explore.smt-lib.org/> 中 QF_UFNIA 已有 `Jaroslav-Bendik-Certora` 与 `certora`。2026 提交仓库：<https://github.com/SMT-LIB/benchmark-submission>。

ctac 文档同时说明 `bytemap-rw` 使用 `Store/Select`，所以“默认编码叫 QF_UFNIA”不是所有输出均符合该理论的证明。必须检查具体输出；涉及数组时应排除，或执行经过论证的 ground 数组消除并保留转换版来源。

## 应用与理论的联系

优先检查常数乘积 AMM 的储备量、兑换数量与池份额计算，以及 Vault 的份额兑换或资产会计性质。AMM 的储备量乘积、符号金额乘符号汇率分子可提供 NIA；按地址读取余额、存储或 bytemap 的操作可能提供 UF。这里列出的是筛选方向，需在实际生成的 VC 中确认，不能因为合约有一个 `*` 就断言性质涉及 NIA。

示意性质可以是储备量乘积在合法兑换后不降低，但费用、舍入、溢出检查和合约版本会改变精确表达式。必须从该版本真实代码和验证规格取得性质，不要用一个抽象的 `x*y=k` 取代完整的实际合约，却仍称其为原样导出。

`uint256` 的变量范围不等于完整的 EVM/Solidity 运算语义。必须保留 checked/unchecked 运算、模回绕、除法、异常与回退、调用环境及外部调用假设的上游编码。若另建无界整数经济模型，应标为应用派生模型，并解释它与原始合约的关系及前提。

## 最小 pilot 与上游输入获取

1. 固定 benchmark、Solidity 编译器、Certora 前端和 ctac 的完整版本。先阅读所选用例的说明、各版本源文件、验证属性和 ground-truth 说明；找到原有 CVL 或该版本支持的规格格式。
2. 先选择一个有明确算术性质的小用例，例如公开 benchmark 中的 tinyamm 候选。记录实际选中的文件路径；不要在尚未检查目录时编造路径或属性名。
3. 确认如何合法取得 TAC dump：复用工程本身公开的 dump，或使用用户环境已有权限运行前端。遵循工具版本的正式导出方式。若需要未提供的授权、远程服务或凭据，不索取/猜测密钥，先继续能做的源码审计并报告准确阻塞点。
4. 在可行时选择一对已有的正确/缺陷版本，针对同一性质形成配对任务。不要凭仓库的“正确”描述预先赋予 SMT 状态；真实模型及编码仍需核验。
5. pilot 先取得 2—10 个完整 VC，确认理论、模型回放和来源链，再考虑大批量生成。

## TAC 到 SMT2 的实施路径

仓库文档中的命令示意如下；执行前需核对锁定版本 `--help` 和前置条件：

```bash
ctac ua input.tac -o single_assert.tac --plain
ctac smt single_assert.tac -o query.smt2 --plain
```

`ua` 处理多断言输入；`ctac smt` 要求 loop-free、single-assert 并满足对应 DSA 条件。遇到循环，不能未经说明删除回边。若使用上游展开或摘要，记录展开界和假设；只有在这些边界内解释结果。首次导出尽量避免额外重写，保留原始 TAC 和原始 SMT；后续简化另存版本以便定位差异。

记录检查点、目标断言、路径可达条件和全部 assumptions。确认查询求解的是“可达且断言失败”，而不是只检查一个没有反例目标的可行状态。若日志中实际存在 push/pop 或多个检查，保存原生序列，并为每个检查构造含活跃断言和 assumptions 的独立快照；不要随意拼接无关合约任务后称为原生增量。

## 筛选、扩展与结果验证

逐文件解析 AST，排除量词、数组、BV、Real、数据类型及其他不属于目标逻辑的内容；删除未用声明可行，但不可删除有约束作用的表达式。要求存在真实非零元 UF 应用及实际非线性整数关系；另外记录它们预处理后是否存活、UF 参数是否含符号整数表达式。不能把范围约束或常数乘法计为真正的变量乘积。

优先从新的真实合约版本、新性质、不同合法调用序列或有实际含义的路径专化扩展。对增加调用深度、账户数量和配置范围的做法，必须明确哪些是前端真实参数，哪些是自行新建 harness。不要假装现有工具支持任意合约的无界完整验证。

- SAT：先用 ctac 文档中的模型回放/验证能力检查 TAC 层面的执行。再尽可能在原始合约测试环境复现，确认不是抽象外部调用、错误环境假设或语义近似导致的伪反例。未完成源合约回放时分层记录证据，不能写成已发现真实漏洞。
- UNSAT：记录精确性质、环境假设、循环界及编码版本；用独立求解器或可检查证明提高可信度。单次超时、`unknown` 或“没有找到攻击”均不能标 `unsat`。
- 正确/缺陷版本属于配对任务，统计和数据划分时保留配对关系，避免把极相似任务分到调参与最终测试两侧。

## 新颖性、可共享性与交付

保存应用仓库和 commit、合约/规格文件、目标性质、TAC 来源、工具版本、完整命令、理论审计、每次语义变换以及回放结果。源码许可证、服务输出的可分享范围与生成文件的许可需分别核对；去掉客户名字或路径不自动获得再分发授权。

先比较 SMT-LIB 原文件 hash，再做去注释、未用声明清理及结构规范化去重；另按原合约版本和性质核查已有应用重叠。仅使用新的工具编码、重命名变量或变更求解器种子，不构成新的应用任务。新日期也不足以证明未收录。

最终交付可重跑脚本、所选公开输入与引用、原始 TAC/SMT（许可允许时）、符合 QF_UFNIA 的输出、被排除任务及原因、元数据和结果证据。若上游 TAC 获取失败，应交付完整已核实路径和阻塞报告，不能手写一个 toy SMT2 冒充工业导出。
